## Game application

`dlGame` is the generic runtime-configured client for Daedalus Engine. It implements `CreateApplication()` with `GameApp`, which installs `GameLayer` to register the Lua adapter and load the selected runtime scene. Gameplay comes from scene records and Lua assets, not compiled example classes.

Build it with any configuration (`Debug`, `Release`, `ReleaseDevTools`, see the root README). The executable is placed in `runtime/bin/<platform>-x64/<Configuration>/`. In Visual Studio, set `dlGame` as the startup project after CMake regenerates the solution. Desktop packages and shortcuts use the name **Daedalus Game**.

Android builds `libdlGame.so` and installs **Daedalus Game** as `org.daedalus.game`. This is a new app identity, not an update of `org.daedalus.sandbox`: the old installation and its private data remain separate. Supply runtime assets/scripts/configuration again for the new app; no private-data migration is performed. See [Android deployment](../../.github/docs/Android.md).

## Runtime scenes

Scene content is loaded entirely from runtime assets, not compiled into the application. Manually place your scene under `runtime/asset` and select it using `SceneFile` in the `[Path]` section of `runtime/path.ini`. The path is relative to the configured `AssetsFolder` (default: `asset`). Without a setting, the application loads `runtime/asset/scenes/startup.scene.json`.

The two JSON files in `scenes/` are examples only; they are not included in the game project or copied automatically. For example, manually copy `scenes/nuke.scene.json` to `runtime/asset/scenes/nuke.scene.json` and set `SceneFile=scenes/nuke.scene.json`. Provide all referenced models, textures, and skybox images under the asset folder as well. Changing the startup scene does not require rebuilding. Missing or invalid scenes log an error and leave the application without an active scene; there is no fallback to an example. See [Scene serialization](../../.github/docs/SceneSerialization.md) for the format and loading workflow.

Lua scripts have a separate `[Path] ScriptsFolder` setting, defaulting to `script` beside `path.ini` (`runtime/script`). The game registers only the built-in `Lua` adapter; both example scenes use it exclusively. Manually copy the contents of `scripts/` into the configured script folder, keeping the filenames unchanged. The Lua files are reference assets on disk only: they are not included in the game project, compiled, or copied by the build. See [Lua scripting](../../.github/docs/Scripting.md) for configuration and binding details.

| Lua example | Behavior |
| --- | --- |
| `camera_controller.lua` | Free camera movement, mouse look and named gamepad look axes. |
| `player_controller.lua` | Camera controls plus player facing, first/third-person view and flashlight toggles. |
| `rotation_model.lua` | Model rotation; `speed` retains degrees per millisecond. |
| `tank_movement.lua` | Back-and-forth patrol with `forward_direction` and `distance` properties. |
| `log_position.lua` | Trace-level camera position logging; available as a reference, not attached in the example scenes. |

Each asset is standalone because module imports and multiple Lua assets per entity are not supported. The Nuke player's single script therefore includes camera control; do not attach a second camera controller to that player. Camera and flashlight entity links are generated by the existing v1 scene migration. Model hiding retains the renderable component, and flashlight toggling preserves its authored power instead of recreating components. The reusable engine-native `CameraController` remains available to other applications but is not registered by dlGame.
